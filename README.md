# dev-guidelines
# SKIB 18 Development Guidelines

Руководство по организации разработки проектов **СКИБ 18**.

Данный репозиторий содержит общие правила ведения проектов, работы с Git и GitHub, оформления документации и организации совместной разработки в СКИБ 18.

Правила распространяются на проекты различных направлений:

- Embedded-разработка;
- разработка электроники и печатных плат;
- механическое проектирование, CAD, печать;
- исследовательские и экспериментальные проекты.

Конкретный проект может использовать только те разделы руководства, которые относятся к его области разработки.

---

## 1. Основные принципы

Разработка проектов СКИБ 18 строится на следующих принципах:

**Воспроизводимость**
Другой участник команды должен иметь возможность получить проект из репозитория и продолжить работу с ним.

**Документирование**
Важные архитектурные, технические и организационные решения должны быть зафиксированы в репозитории.

**Контроль изменений**
Изменения проекта выполняются через Git и должны иметь понятную историю.

**Командная разработка**
Основная ветка проекта не используется для непосредственной разработки новых функций.

**Ответственность**
Каждый проект имеет ответственного руководителя, который контролирует развитие проекта и принимает изменения в основную ветку.

---

## 2. Организация проектов

Каждый самостоятельный проект СКИБ 18 размещается в отдельном GitHub-репозитории.

Например:

```text
SKIB-18/
├── project-a
├── project-b
├── project-c
└── ...
```

Администратор организации создаёт репозиторий проекта, выполняет его первоначальную настройку и предоставляет доступ участникам команды.

Внутренняя структура репозитория определяется командой проекта с учётом требований настоящего руководства.

Проект может содержать, например:

```text
project/
├── firmware/
├── hardware/
├── mechanical/
├── software/
├── docs/
└── README.md
```

Наличие всех перечисленных директорий не является обязательным.

Структура должна соответствовать реальному составу проекта.

---

## 3. Роли

### Administrator

Администратор отвечает за инфраструктуру GitHub-организации СКИБ 18.

В его задачи входят:

- создание новых репозиториев;
- первоначальная настройка репозиториев;
- управление командами и правами доступа;
- назначение руководителей проектов;
- настройка защиты веток;
- архивирование завершённых проектов;
- поддержание общей структуры организации.

Администратор не обязан контролировать каждое изменение внутри отдельных проектов.

---

### Project Lead

Руководитель проекта отвечает за конкретный проект.

В его задачи входят:

- организация работы команды;
- определение структуры репозитория;
- распределение задач;
- контроль Pull Request;
- проведение или организация Code Review;
- поддержание основной ветки проекта в рабочем состоянии;
- контроль документации проекта;
- подготовка релизов.

---

### Contributor

Участник проекта выполняет задачи в рамках проекта.

В его задачи входят:

- работа в отдельных ветках;
- создание понятных коммитов;
- соблюдение структуры проекта;
- обновление документации при необходимости;
- создание Pull Request;
- исправление замечаний после Review.

---

## 4. Базовый процесс разработки

Стандартный процесс работы над задачей:

```text
Issue / задача
      │
      ▼
Создание ветки
      │
      ▼
Разработка
      │
      ▼
Commit
      │
      ▼
Push
      │
      ▼
Pull Request
      │
      ▼
Review
      │
      ▼
Merge
      │
      ▼
main
```

Разработка новой функциональности непосредственно в `main` не выполняется.

Для каждой отдельной задачи создаётся отдельная ветка.

Например:

```text
feature/can-driver
fix/adc-measurement
docs/assembly-guide
hardware/power-board
```

После завершения работы участник создаёт Pull Request.

Изменения проверяются руководителем проекта или назначенным участником команды и после одобрения объединяются с основной веткой.

---

## 5. Основная ветка

Основной веткой проектов СКИБ 18 является:

```text
main
```

`main` должна содержать актуальное и работоспособное состояние проекта.

Прямые изменения `main` участниками проекта не допускаются.

Изменения должны попадать в `main` через Pull Request.

---

## 6. Коммиты

Сообщение коммита должно кратко и понятно описывать внесённое изменение.

Рекомендуемый формат:

```text
<тип>: <описание>
```

Примеры:

```text
feat: добавлен драйвер CAN

fix: исправлен расчёт напряжения АЦП

docs: добавлена инструкция по сборке

test: добавлены тесты UART

refactor: упрощена логика определения состояния аккумулятора
```

Для инженерных изменений могут использоваться дополнительные типы:

```text
pcb: обновлена разводка платы питания

sch: добавлена схема защиты аккумулятора

cad: обновлена модель корпуса

```

Тип коммита записывается на английском языке для сохранения единого стандартного формата. Описание изменения пишется на русском языке.

Подробные требования к оформлению коммитов приведены в разделе **Git / Commits**.

---

## 7. Документация проекта

Каждый проект должен содержать файл:

```text
README.md
```

README должен позволять новому участнику понять:

- назначение проекта;
- текущее состояние разработки;
- структуру проекта;
- используемые технологии;
- необходимое оборудование;
- способ сборки или запуска проекта;
- расположение основной документации.

Для сложных проектов дополнительная документация размещается в:

```text
docs/
```

## 9. Главное правило

Репозиторий проекта должен быть организован так, чтобы другой участник СКИБ 18 мог получить проект, разобраться в его структуре, собрать или открыть его и продолжить разработку без необходимости восстанавливать устройство проекта исключительно со слов предыдущего разработчика.
