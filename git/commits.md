# Правила оформления коммитов

Данный документ устанавливает правила оформления коммитов в проектах **СКИБ 18**.

Понятная история коммитов позволяет быстро определить, какие изменения были внесены в проект, кем и с какой целью.

---

## 1. Формат сообщения

Для сообщений коммитов используется следующий формат:

```text
<тип>: <краткое описание изменения>
```

Например:

```text
feat: добавлен драйвер CAN
fix: исправлен расчёт напряжения аккумулятора
docs: обновлена инструкция по сборке
pcb: изменена разводка платы питания
cad: обновлена модель корпуса
```

Тип коммита записывается **на английском языке**, описание изменения — **на русском языке**.

---

## 2. Типы коммитов

### `feat`

Добавление новой функциональности.

```text
feat: добавлена поддержка датчика температуры
feat: реализована передача данных по CAN
feat: добавлено управление двигателем
```

---

### `fix`

Исправление ошибки или неправильного поведения существующей системы.

```text
fix: исправлен расчёт напряжения АЦП
fix: устранена ошибка инициализации UART
fix: исправлена обработка потери связи
```

---

### `docs`

Изменение документации без изменения самого устройства или программной логики.

```text
docs: добавлена инструкция по прошивке
docs: обновлено описание интерфейса CAN
docs: добавлена схема подключения устройства
```

---

### `refactor`

Изменение внутренней структуры программного кода без добавления новой функциональности и исправления конкретной ошибки.

```text
refactor: переработана структура драйвера UART
refactor: упрощена обработка состояний устройства
```

---

### `test`

Добавление или изменение тестов.

```text
test: добавлены тесты драйвера UART
test: добавлена проверка обработки ошибок CAN
```

---

### `pcb`

Изменение печатной платы.

```text
pcb: изменена разводка цепи питания
pcb: изменено расположение разъёмов
pcb: обновлена трассировка сигнальных линий
```

---

### `sch`

Изменение электрической принципиальной схемы.

```text
sch: добавлена защита от переполюсовки
sch: изменена схема питания микроконтроллера
sch: добавлен CAN-трансивер
```

---

### `cad`

Изменение механической части проекта, CAD-моделей или чертежей.

```text
cad: изменены размеры корпуса
cad: добавлено крепление печатной платы
cad: обновлена сборочная модель
```

---

### `chore`

Технические изменения, которые непосредственно не изменяют функциональность проекта.

Например:

```text
chore: обновлён gitignore
chore: изменена структура каталогов
chore: удалены устаревшие файлы
```

---

## 3. Основные требования

Сообщение коммита должно быть:

- кратким;
- понятным;
- связанным с конкретным изменением;
- достаточным для понимания сути изменения без просмотра всех изменённых файлов.

Хорошо:

```text
feat: добавлено измерение напряжения аккумулятора
```

Плохо:

```text
изменения
```

Плохо:

```text
fix
```

Плохо:

```text
что-то исправил
```

Плохо:

```text
final
```

---

## 4. Один коммит — одно логическое изменение

В один коммит рекомендуется включать изменения, относящиеся к одной задаче.

Например, если разработчик:

1. добавил драйвер CAN;
2. исправил ошибку измерения напряжения;
3. обновил инструкцию по сборке;

рекомендуется создать отдельные коммиты:

```text
feat: добавлен драйвер CAN

fix: исправлено измерение напряжения

docs: обновлена инструкция по сборке
```

Не рекомендуется объединять независимые изменения в один коммит:

```text
feat: добавлен CAN, исправлен АЦП и обновлена документация
```

Это позволяет проще просматривать историю проекта и при необходимости находить или отменять отдельные изменения.

---

## 5. Размер коммита

Не следует искусственно создавать коммит после изменения каждой строки или каждого файла.

Коммит создаётся после завершения **логически законченной части работы**.

Например, при разработке драйвера периферии один коммит может содержать:

```text
drivers/can.c
drivers/can.h
```

если оба файла относятся к одной реализации.

При этом не следует ждать полного завершения большого проекта, чтобы создать единственный огромный коммит.

---

## 6. Проверка перед коммитом

Перед созданием коммита необходимо проверить состояние репозитория:

```bash
git status
```

При необходимости можно посмотреть внесённые изменения:

```bash
git diff
```

После проверки нужные файлы добавляются:

```bash
git add <файл>
```

или:

```bash
git add .
```

После этого создаётся коммит:

```bash
git commit -m "feat: добавлен драйвер CAN"
```

Перед использованием `git add .` необходимо убедиться, что в коммит не попадут временные, автоматически сгенерированные или другие ненужные файлы.

---

## 7. Связь коммита с задачей

Если работа выполняется в рамках Issue, номер задачи при необходимости может быть указан в сообщении коммита.

Например:

```text
feat: добавлено измерение напряжения аккумулятора (#24)
```

Основную информацию о выполненной задаче и её закрытии рекомендуется указывать в Pull Request.

---

## 8. Изменения разных частей проекта

Инженерный проект может одновременно содержать программную, электронную и механическую части.

В этом случае тип коммита выбирается по основной сути изменения.

Например:

```text
sch: добавлена цепь измерения напряжения

pcb: добавлена цепь измерения напряжения на плату

feat: добавлена обработка измерения напряжения в прошивке

cad: добавлено отверстие под новый разъём

docs: обновлена документация устройства
```

Таким образом история репозитория позволяет быстро понять, какая часть проекта изменялась.

---

## 9. Краткая памятка

Основные типы коммитов:

```text
feat      — новая функциональность
fix       — исправление ошибки
docs      — документация
refactor  — переработка кода
test      — тесты
sch       — электрическая схема
pcb       — печатная плата
cad       — механика и CAD
chore     — технические изменения
```

Формат:

```text
<тип>: <описание на русском языке>
```

Пример:

```text
feat: добавлен драйвер CAN
```

Главный принцип:

> По сообщению коммита должно быть понятно, что изменилось в проекте.
