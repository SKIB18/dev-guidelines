# Рабочий процесс Git

Данный документ описывает стандартный порядок работы с Git и GitHub в проектах **СКИБ 18**.

Цель рабочего процесса — обеспечить понятную историю разработки, разделение задач между участниками и контроль изменений, попадающих в основную ветку проекта.

---

## 1. Общая схема работы

Работа над изменением проекта выполняется по следующей схеме:

```text
Задача / Issue
      │
      ▼
Создание отдельной ветки
      │
      ▼
Разработка
      │
      ▼
Commit
      │
      ▼
Push
      │
      ▼
Pull Request
      │
      ▼
Review
      │
      ▼
Merge
      │
      ▼
main
```

Разработка непосредственно в ветке `main` не выполняется.

---

## 2. Получение проекта

Перед началом работы необходимо получить локальную копию репозитория.

```bash
git clone <URL-репозитория>
```

После клонирования необходимо перейти в директорию проекта:

```bash
cd <название-репозитория>
```

Если репозиторий уже был клонирован ранее, перед началом новой работы необходимо получить актуальные изменения:

```bash
git switch main
git pull
```

Таким образом новая работа начинается от актуального состояния `main`.

---

## 3. Создание задачи

Для значимых изменений рекомендуется предварительно создать **Issue** в GitHub.

Issue должен описывать конкретную задачу.

Например:

```text
Добавить поддержку CAN
```

или:

```text
Исправить неправильное измерение напряжения аккумулятора
```

Issue используется для обсуждения задачи, фиксации требований и отслеживания её выполнения.

Для небольших очевидных изменений создание Issue может не требоваться по решению руководителя проекта.

---

## 4. Создание рабочей ветки

Для выполнения задачи создаётся отдельная ветка от актуальной `main`.

Например:

```bash
git switch main
git pull
git switch -c feature/can-driver
```

После этого разработка выполняется в созданной ветке.

Примеры названий:

```text
feature/can-driver
fix/adc-measurement
docs/assembly-guide
hardware/power-board
cad/enclosure
```

Одна ветка должна соответствовать одной логически завершённой задаче.

Подробные правила именования веток приведены в документе `branches.md`.

---

## 5. Выполнение работы

Участник выполняет необходимые изменения в своей рабочей ветке.

Это может быть:

- изменение исходного кода;
- добавление драйвера;
- изменение электрической схемы;
- трассировка печатной платы;
- изменение CAD-модели;
- создание чертежей;
- проведение расчётов;
- изменение документации.

После выполнения логически завершённой части работы необходимо проверить изменённые файлы:

```bash
git status
```

---

## 6. Добавление изменений

Необходимые файлы добавляются в индекс Git:

```bash
git add <файл>
```

Для добавления нескольких файлов:

```bash
git add <файл-1> <файл-2>
```

Добавление всех изменённых файлов:

```bash
git add .
```

Перед использованием `git add .` необходимо убедиться, что в репозиторий не попадут временные, автоматически сгенерированные или другие ненужные файлы.

Для этого используется `.gitignore`.

---

## 7. Создание коммита

После добавления файлов создаётся коммит:

```bash
git commit -m "feat: добавлен драйвер CAN"
```

Другие примеры:

```bash
git commit -m "fix: исправлен расчёт напряжения"

git commit -m "docs: добавлена инструкция по сборке"

git commit -m "pcb: обновлена разводка платы питания"

git commit -m "cad: обновлена модель корпуса"
```

Один коммит должен представлять одно логически завершённое изменение.

Подробные правила оформления коммитов приведены в документе `commits.md`.

---

## 8. Отправка ветки на GitHub

После создания коммитов рабочая ветка отправляется на GitHub:

```bash
git push -u origin feature/can-driver
```

При последующих изменениях этой же ветки достаточно использовать:

```bash
git push
```

---

## 9. Создание Pull Request

После завершения задачи участник создаёт **Pull Request** из своей рабочей ветки в `main`.

Например:

```text
feature/can-driver
        │
        │ Pull Request
        ▼
       main
```

В Pull Request необходимо кратко описать:

- что было сделано;
- зачем было сделано изменение;
- как изменение было проверено;
- есть ли особенности, которые необходимо учитывать при проверке.

Если Pull Request связан с Issue, необходимо указать соответствующую задачу.

---

## 10. Review

Pull Request проверяется руководителем проекта или назначенным участником команды.

Во время Review могут проверяться:

- корректность реализации;
- структура проекта;
- качество исходного кода;
- схемы и PCB;
- CAD-модели;
- документация;
- наличие необходимых файлов;
- результаты тестирования.

Если обнаружены проблемы, проверяющий оставляет комментарии.

Автор Pull Request вносит исправления в **ту же рабочую ветку**:

```bash
git add .
git commit -m "fix: исправлены замечания после проверки"
git push
```

Pull Request обновится автоматически.

Создавать новый Pull Request для исправления замечаний не требуется.

---

## 11. Объединение с main

После успешного Review изменения могут быть объединены с `main`.

```text
Рабочая ветка
      │
      ▼
Pull Request
      │
      ▼
Review
      │
      ▼
Approve
      │
      ▼
Merge
      │
      ▼
main
```

Решение о принятии Pull Request принимает руководитель проекта или участник, имеющий соответствующие права.

---

## 12. Удаление рабочей ветки

После успешного Merge рабочая ветка больше не требуется и должна быть удалена.

Удалить удалённую ветку можно непосредственно через интерфейс GitHub после Merge.

Локальную ветку можно удалить командой:

```bash
git branch -d feature/can-driver
```

После этого рекомендуется обновить локальную `main`:

```bash
git switch main
git pull
```

Участник готов к выполнению следующей задачи.

---

## 13. Полный цикл

В результате стандартный цикл работы участника СКИБ 18 выглядит следующим образом:

```text
Получить задачу
      │
      ▼
Обновить main
      │
      ▼
Создать рабочую ветку
      │
      ▼
Выполнить работу
      │
      ▼
Проверить изменения
      │
      ▼
Создать коммит
      │
      ▼
Push
      │
      ▼
Создать Pull Request
      │
      ▼
Пройти Review
      │
      ▼
Merge в main
      │
      ▼
Удалить рабочую ветку
      │
      ▼
Обновить локальную main
```

---

## 14. Основные правила

1. Не вести обычную разработку непосредственно в `main`.
2. Одна задача — одна рабочая ветка.
3. Перед созданием новой ветки обновлять `main`.
4. Не добавлять в репозиторий временные и ненужные файлы.
5. Делать логически понятные коммиты.
6. Перед отправкой изменений проверять `git status`.
7. Изменения в `main` вносить через Pull Request.
8. Pull Request должен пройти Review.
9. После Merge удалять завершённую рабочую ветку.
10. Поддерживать документацию проекта в актуальном состоянии.
